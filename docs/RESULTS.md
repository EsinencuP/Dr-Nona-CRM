## Фактические показатели

- Когорта: `Order.type = order`, `Order.status = DONE`, время **создания** заказа. Отдельного `completedAt` в существующей модели нет; не подменять его `updatedAt`. Консультации, мастер-классы, незавершённые и отменённые заявки не считаются продажами.
- `1m/3m/6m/1y` — последние 30/90/180/365 × 24 часа, включая начало и исключая конец. Сравнение с непосредственно предыдущим окном той же длины. В интерфейсе время Europe/Chisinau; это скользящие интервалы, не календарные месяцы. Неизвестный или повторённый URL-параметр возвращает `1m`.
- Доход: сумма количества × `retailPriceAtPurchase`. Закупка: количества × `distributorPriceAtPurchase`. Суммирование в целых банях; интерфейс округляет денежные значения до целых MDL, как в задании.
- «Чистая прибыль» в рамках задания: доход минус закупка. Доставка, налоги и иные расходы не включены; это не полный бухгалтерский результат.
- Средний чек: доход / число завершённых товарных заказов; при отсутствии заказов — 0. Абсолютная дельта = текущее − прошлое; процент = дельта / модуль прошлого × 100. При нулевой базе или неизвестном значении процент «—».
- Нулевые снимки — **нет данных**, а не бесплатная продажа. Если хотя бы один заказ в периоде имеет неизвестную розницу, денежный итог дохода и среднего чека недоступен. Неизвестная закупка блокирует прибыль. Число неполных заказов показано отдельно для каждого периода. Единицы продаж продолжают учитываться. Некорректное количество исключается из единиц и делает денежный итог неполным.
- Регионы: 36 значений из общего справочника плюс отдельная группа для нераспознанного значения. Используется текущий `Client.region`; изменение карточки клиента изменит региональную группировку истории. Имена, телефоны, email и идентификаторы клиентов не выбираются сервисом и не передаются в Client Components.

## Прогноз и рекомендации

Прогноз всегда использует последние 90 дней независимо от выбранного периода отчётности:

1. Разделить продажи на три последовательных окна по 30 дней.
2. Скорость = 0,5 × последние 30 дней + 0,3 × предыдущие + 0,2 × ранние.
3. Рост = последние / предыдущие − 1; ограничить −0,5…+0,5. Если база нулевая — рост 0, без искусственного взрыва прогноза.
4. Месяц N = округление вверх скорости × (1 + рост)^N, N = 1, 2, 3. Это отдельные месяцы, не накопительные продажи.
5. Рекомендуемый заказ = округление вверх прогноза месяца 1 × 1,15. Это потребность до вычета складских остатков и поставок в пути, которых в CRM нет. Итоговую закупку подтверждает менеджер.

Веса, предел роста и сезонные даты — явные правила планирования, не обученная модель и не доказанные свойства спроса. Короткая история, возвраты и смена статусов снижают надёжность. Ноль не доказывает отсутствие будущего спроса.

Мастер-классы: только товары с двумя известными утверждёнными ценами и положительной маржой в MDL; скорость не выше среднего по ассортименту, сортировка по марже, до трёх рекомендаций. Драйверы объёма: до трёх товаров с реальными ненулевыми продажами выбранного периода. Исторический неизвестный slug сохраняется в таблице, но не получает выдуманные цены.

Сезонные правила строятся только для существующих товаров: Solaris к 1 апреля, Gonseen Tea и категория «Пищевые добавки» к 1 октября; подготовка за 45–30 дней. После наступления даты целевой сезон переносится на следующий год. Напоминание остаётся активным от начала подготовки до сезона. Карточки содержат только мероприятия и закупочное планирование, без медицинских обещаний, скидок и изменения цен.

## Цены и миграция

Добавлены четыре поля из задания с default 0. Миграция аддитивная: не удаляет и не восстанавливает старые данные. `internalPrice` остаётся историческим полем и не используется в новой аналитике: одной старой цены недостаточно для определения розницы и закупки.

Менеджер в `/catalog` вносит **уже утверждённые** розничную и закупочную цены. Server Action проверяет доступ, slug опубликованного товара, обе положительные конечные суммы до 1 000 000 MDL и точность до двух десятичных знаков. Автоматического изменения цен и советов по ценообразованию нет.

Новый заказ читает обе цены из ProductCatalog внутри той же транзакции, что и создание клиента/заказа. Клиентский payload не задаёт цены. Снимки старых заказов не меняются после редактирования каталога или смены статуса. Legacy `priceAtPurchase` зеркалирует розничный снимок только для новых заказов, сохраняя совместимость старых экранов. Старые `internalPrice` и `priceAtPurchase` не переписываются. Порядок persistence-before-Telegram сохранён.

Перед запуском новой версии:

```powershell
npm run db:generate
npm run db:migrate:deploy
npm run typecheck
npm run lint
npm run check
npm run test
npm run build
```

Использовать direct `DATABASE_URL_UNPOOLED` для миграций, pooled `DATABASE_URL` для приложения. Сначала проверить на изолированной тестовой базе; тесты интеграции записывают свои временные заказы. Не запускать их с production URL. Не разворачивать код, читающий новые столбцы, раньше миграции. Заполнение утверждённых цен и документально подтверждённое восстановление исторических снимков — отдельные реальные операции, не автоматический backfill.
