# CRM popularity feed and Excel reports

Owner decision: 2026-09-16. The catalogue keeps the RU/RO “By popularity” sort, using the number of **distinct completed real orders containing a product** during a rolling 90-day window. Quantity and repeated lines within one order do not increase that product's order-occurrence count. Orders are included by creation time because the CRM does not store a reliable historical completion timestamp. A late status change can change the next candidate. Cancelled, other request types, future, out-of-window and `demo-*` orders are excluded. Prices do not affect popularity.

The private bearer-protected `GET /api/internal/popularity-candidate` produces only an aggregate candidate. It queries the CRM database and checks each slug against the published CRM catalogue. Unknown slugs appear in `quarantinedSlugs` and make the candidate ineligible. It includes no name, phone, email, order ID, client ID or price. A candidate is `ready` only with at least 10 eligible real orders from at least 5 distinct clients and no quarantined slugs. It expires after seven days. Equal counts use the catalogue's `officialOrder`, then SKU. With fewer orders, the catalogue's visible fallback is the official order and never a fabricated popularity claim.

The separate catalogue repository fetches the candidate once daily through a GitHub Actions schedule, validates the strict schema and all 50 published slugs, and prepares a snapshot on `automation/popularity-90d` only if the order changes or the current snapshot nears expiry. A human opens and reviews a pull request from that branch; **merging the PR is publication approval**. The catalogue includes the reviewed snapshot at build time and makes no runtime request to the CRM or its database. The public snapshot contains order of slugs and a digest, not customer data or exact order counts. It automatically falls back when expired. A failed fetch, unknown slug, too-small sample or unmerged branch leaves the last reviewed snapshot in place until expiry, then the official-order fallback applies. Rollback is a revert of the snapshot commit; `src/data/popularity-snapshot.json` can always be returned to `mode: "fallback"`.

Configuration: `POPULARITY_EXPORT_TOKEN` must be a strong secret in the CRM production Vercel environment and the catalogue GitHub Actions repository secrets. The CRM route fails closed if the secret is absent or shorter than 32 characters. The scheduled action cannot read general CRM Basic Auth credentials. GitHub currently does not permit Actions to open pull requests, so the workflow deliberately publishes only the review branch and prints the compare URL. Do not merge a candidate after its seven-day expiry.

The protected CRM Excel export is available from `/orders`, `/clients` and `/results`. The manager chooses one of four reports (orders, clients, products, regions), an optional Moldova-local inclusive date range, and any approved subset of columns in the pop-up. `includeDemo` is off by default; `demo-*` orders and clients are excluded unless the manager explicitly selects them. Orders use immutable submitted contact/region snapshots. Client reports use the current client profile and count orders within the selected period. Product reports count each completed order containing a product once. No public catalogue response contains customer records or internal prices.

The server enforces the report/column allowlist, same-origin POST, CRM Basic Auth, a 366-day maximum when both dates are supplied, and 10,000 source rows. A larger report is rejected rather than silently truncated. Blank price cells mean a required historical snapshot is missing; totals and margin are not invented. Dates are interpreted in `Europe/Chisinau`, including daylight-saving transitions. Only `.xlsx` is produced; there is no CSV or PDF path. Untrusted text is encoded as XLSX `inlineStr` so a value beginning with `=` cannot become a workbook formula. The file is generated in memory and returned with `private, no-store`; no server-side report file is retained. A `ReportExportAudit` row records creation or failure, actor, report, selected column keys, date range, demo option, row count and file size, without exported values. An audit write failure prevents the download.

The export uses the existing single CRM Basic Auth manager. It does not introduce additional roles or claim that a downloaded personal-data file can be recalled. The manager is responsible for secure handling after download. The production workbook is not a financial ledger: missing price snapshots and excluded delivery, tax and other costs remain explicit limitations.
