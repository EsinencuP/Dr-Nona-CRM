# Dashboard: операционная сводка

Дата проверки: 2026-09-12. Задание владельца: `dashboard_redesign_prompt.md`, Master-Prompt Dashboard Redesign — Dr. Nona CRM Moldova. Целевая страница — `/dashboard` в отдельном репозитории CRM.

**Локальная реализация и QA: PASS на базе с применёнными миграциями. Развёртывание: не выполнено.** Стандартное окружение пока не содержит полей цен предыдущего этапа `/results`; это реальное условие запуска, а не закрытый production blocker.

## Что реализовано

- Четыре KPI: выручка, принятые заявки, проданные единицы, новые клиенты; абсолютные и процентные изменения относительно равного предыдущего окна.
- URL-периоды `7d`, `30d`, `90d`, `all`. Все аналитические виджеты и последние восемь заявок используют выбранный период.
- Отдельные текущие счётчики NEW / PROCESSING / DELIVERY / CANCELLED по всем заявкам, с переходом в существующий фильтр `/orders`. Это снимок на момент загрузки, без фонового опроса; время загрузки и инструкция обновления видимы.
- Совмещённый график заявок и выручки с двумя осями; топ-5 товаров; топ-8 регионов; источники заявок с пятью группами максимум; 24 почасовых столбца по Europe/Chisinau.
- Лента последних восьми заявок с существующим StatusBadge, относительным временем и переходом `/orders?search=id`.
- Дополнительные итоги: выполненные заявки, конверсия, средний чек, доход минус закупка, стоимость отменённых продаж.
- Состояния загрузки, пустых данных, неполных цен и ошибки базы с действующим повтором загрузки. Табличные/текстовые альтернативы графиков, управление периодами с клавиатуры.
- Manrope, локальная палитра задания, тонкие границы и лёгкие тени. На 1440 px — четыре KPI, основной ряд 2+1 и нижний ряд из трёх виджетов; на 768 px — два KPI и последовательные графики; на 375 px — одна колонка.

Sidebar, StatusBadge, остальные страницы, публичный e-catalog, API и схема БД в этом задании не изменялись. Сервис дашборда и общий тип результата изменены в явно разрешённых заданием файлах. Финансовые данные доступны за существующей CRM-авторизацией.

## Решения по противоречиям задания

1. Таблица KPI связывала «Заявок принято» с `done`, хотя `total` также требовался. Название отображает все поступившие заявки, а DONE отдельно показан как «Выполнено заявок». Это явно выбранная интерпретация, не новый статус.
2. Ранние примеры требовали две мобильные колонки, финальная acceptance-матрица — одну. Применена финальная матрица; tablet charts остаются последовательными.
3. Процент при нулевой предыдущей базе — «—», без искусственного делителя 1. Абсолютное изменение остаётся доступно. `all` не получает выдуманный предыдущий период. Поэтому тип дельты допускает `null`.
4. Для доступности мелкие ссылки используют тёмный подчёркнутый текст, активная вкладка — светлый синий фон и синюю границу. Нейтральные бейджи используют slate-50 вместо slate-100: исходное сочетание давало контраст 4,34:1. Акценты из задания закреплены точными HEX в локальном CSS-модуле, так как Tailwind v4 использует другие значения по умолчанию.
5. Подсветка часов 9–12 и 17–21 сохранена как условная визуальная подсказка. Реальный максимум рассчитан отдельно из данных и подписан; эти интервалы не представлены как доказанный пик.
6. Упомянутые в задании три изображения-референса не были доступны. Проверено соответствие текстовой спецификации, не визуальное совпадение с отсутствующими референсами.

## Формулы и границы данных

Периоды — последние 7/30/90 × 24 часа: начало включено, конец исключён. Предыдущее окно имеет ту же длину. Запросы используют единый `now` и транзакцию RepeatableRead. В режиме `all` временная группировка помесячная, в ограниченных периодах — по местным датам, включая нулевые интервалы. Отдельного `completedAt` нет: используется дата создания заявки и её текущий статус.

Количество заявок, конверсия, регионы, источники и часы включают все типы заявок. Продажи, единицы, средний чек и топ товаров учитывают только `type=order`, `status=DONE`. Доход = сумма округлённой до баней розничной цены × количество. Маржа = сумма (розница − закупка) × количество; доставка, налоги и другие расходы не включены. Средний чек делит выручку на число завершённых товарных заказов. Отменённые продажи считаются отдельно и не вычитаются из выручки.

Нулевые или невалидные цены не считаются бесплатной продажей. Согласно этому заданию дашборд показывает **частичную сумму известных снимков** и предупреждение. Прибыль включает только позиции с обеими известными ценами. Неполная розница отключает сравнение выручки и среднего чека, неполная закупка также отключает сравнение прибыли. Проверяется и текущий, и предыдущий период. В `/results` сохранена более строгая прежняя политика: неполный денежный итог недоступен. Не унифицировать эти политики без отдельного решения владельца.

Регионы берутся из текущей карточки клиента, поэтому её редактирование меняет историческую группировку. Неизвестный SKU сохраняется под своим slug. Пустой UTM нормализуется в «Прямой переход»; при количестве источников больше пяти четыре лидера сохраняются, остальные суммируются в «Другие» без потери общего количества.

`requireCrmAccess()` вызывается до запросов. Агрегаты не выбирают телефоны/email; имена и ID выбираются только для ленты из восьми заявок. Снимки цен читаются из существующих OrderItem, не подменяются текущими ценами каталога. Внешних API-вызовов и рекомендаций по изменению цен нет.

## Что остаётся перед запуском

1. Применить существующую миграцию `20260912000000_results_fixed_prices` к целевой базе согласованным deployment-процессом. При запуске `npm run test` без изолированных URL обнаружены отсутствующие `ProductCatalog.retailPrice` и другие новые поля: 178 тестов прошли, два интеграционных упали. Это не исправлялось удалением тестов или автоматическим изменением рабочей базы.
2. Внести утверждённые цены через существующий `/catalog`. Исторические снимки автоматически не восстанавливаются. Дашборд обозначает неполноту данных, пока она сохраняется.
3. Выполнить CI, развёртывание и authenticated runtime-проверку на целевом окружении. Они в этом задании не выполнялись; локальный PASS не означает production-ready.

Для воспроизведения тестов сначала явно задать `DATABASE_URL` и `DATABASE_URL_UNPOOLED` отдельной тестовой базы, затем выполнить `npm run db:migrate:deploy`, `npm run db:generate`, `npm run typecheck`, `npm run lint`, `npm run check`, `npm run test`, `npm run build`. Не использовать рабочую базу как источник синтетических fixture-записей.
